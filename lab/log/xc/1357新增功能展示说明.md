## 1. null：补齐数据库 NULL 基础语义

### 1.1 功能目标

`null` 是后续很多 SQL 功能的语义基础。没有 NULL 支持时，数据库只能表达“有值”，不能表达“未知、缺失或不适用”。本任务目标是让 miniOB 支持：

- 建表时声明字段允许 `NULL` 或 `NOT NULL`。
- 插入和更新时检查 `NOT NULL` 约束。
- 查询时支持 `IS NULL` 与 `IS NOT NULL`。
- 普通比较遇到 NULL 时按 unknown 语义处理，不能误判为 true。
- 聚合函数能正确跳过 NULL。
- 索引列出现 NULL 时保持索引路径和全表扫描路径语义一致。

展示时可以把它理解为“给 miniOB 的每一行记录增加一份缺失值地图”，后续表达式、聚合、索引都要参考这份地图。

### 1.2 为什么这样设计

XC 采用的是在 row record 中增加 `null bitmap` 的方案。也就是说，每条记录除了原本字段 payload，还额外保存一段位图，用一个 bit 标识一个用户字段是否为 NULL。

设计取舍如下：

- `null bitmap` 只覆盖用户列，不覆盖系统事务列，避免影响系统内部字段。
- record 布局调整为 `[null bitmap][field payloads...]`，字段 payload 整体后移。
- 字段元数据 `FieldMeta` 增加 `nullable`，表元数据序列化时也保存 nullable 属性。
- 旧表文件不做兼容，因为记录物理布局已经改变；验证前需要清空旧数据库目录。
- 单列索引遇到 NULL 键时跳过索引项，不额外设计 NULL 键编码，避免 B+Tree 比较逻辑复杂化。

这个设计的好处是语义比较清晰：NULL 状态独立保存，不需要用特殊 int、特殊字符串或特殊浮点值来伪装 NULL。缺点是会改变记录物理布局，因此旧数据文件需要清空后重新生成。

从数据库概念上看，这里要区分两件事：

- `nullable` 是 schema 级别约束，表示“这一列是否允许为空”。
- `null bitmap` 是 record 级别状态，表示“这一行这一列当前是不是空”。

这两个信息不能混在一起。比如某列允许 NULL，只代表它可以为空；具体某一行是不是 NULL，还得看这一行记录里的 bitmap。

### 1.3 实现主链

`null` 的实现链路跨越 parser、元数据、存储、表达式、聚合和索引几个层次：

- Parser / AST：识别 `NULL`、`NOT NULL`、`IS NULL`、`IS NOT NULL` 等语法，把字段是否允许为空记录到建表属性中。
- Value / Expression：让 `Value` 能表达 NULL，并让比较表达式在遇到 NULL 时返回 unknown/false 过滤语义。
- FieldMeta / TableMeta：字段元数据增加 `nullable`，表元数据序列化和反序列化同步保存该属性。
- Table / Record / Tuple：写入记录时维护 null bitmap，读取 tuple 时能根据 bitmap 判断字段是否为 NULL。
- Insert / Update：写入前检查目标字段是否 `NOT NULL`，如果写入 NULL 则返回错误。
- Aggregator：聚合函数处理输入时跳过 NULL，避免把缺失值当成普通值参与计算。
- Index：NULL 索引键不写入单列索引项，保证通过索引查询时不会把 NULL 键误匹配为普通值。

关键代码锚点：

- `src/observer/sql/parser/yacc_sql.y`：`attr_def` 规则把 `NULL / NOT NULL` 写入 `AttrInfoSqlNode::nullable`，`value` 规则把 SQL `NULL` 转成空值 `Value`。
- `src/observer/storage/field/field_meta.*`：`FieldMeta` 增加 `nullable_`，并在 JSON 元数据中序列化。
- `src/observer/storage/table/table_meta.*`：计算 `null_bitmap_offset_` 和 `null_bitmap_size_`，提供 `field_is_null` / `set_field_null`。
- `src/observer/storage/table/table.cpp`：`Table::make_record` 写记录时检查 `NOT NULL`，并设置 bitmap。
- `src/observer/sql/expr/tuple.h`：`RowTuple::cell_at` 读记录时先看 bitmap，如果为空就返回 `Value::set_null(type)`。
- `src/observer/sql/expr/expression.cpp`：`ComparisonExpr::compare_value` 处理 `IS NULL / IS NOT NULL`，普通比较遇到 NULL 返回 false。

以一条 SQL 为例：

```sql
CREATE TABLE t(id INT NOT NULL, score INT NULL);
INSERT INTO t VALUES (1, NULL);
SELECT * FROM t WHERE score IS NULL;
```

执行思路可以这样讲：

1. 建表时，parser 在 `AttrInfoSqlNode` 上记录 `id.nullable=false`、`score.nullable=true`。
2. 初始化 `TableMeta` 时，系统事务字段后面先留出 null bitmap，再安排用户字段 payload offset。
3. 插入时，`Table::make_record` 发现 `score` 的 `Value` 是 NULL，于是在 bitmap 里把 `score` 对应 bit 置 1，不写普通 payload。
4. 查询时，`RowTuple::cell_at` 读到该 bit 为 1，就返回一个 NULL 类型的 `Value`。
5. `ComparisonExpr` 执行 `IS NULL`，直接检查 `Value::is_null()`，结果为 true。

### 1.4 边界语义

`null` 最容易出错的地方不是语法，而是语义边界：

- `NULL = NULL` 不应该当成 true；普通比较只要任一侧为 NULL，就不应通过 WHERE 过滤。
- `IS NULL` 和 `IS NOT NULL` 是专门判断 NULL 的语法，不能简单复用 `=` 或 `<>`。
- `NOT NULL` 字段在 INSERT 和 UPDATE 时都要检查，不能只检查 INSERT。
- 聚合函数需要跳过 NULL，尤其是 `count(expr)`、`sum`、`avg` 这类函数。
- 旧表文件与新 record 布局不兼容，测试前需要清理旧数据库目录。

一个容易向老师解释清楚的点是：普通比较和 `IS NULL` 不能共用一套逻辑。

```sql
score = NULL      -- 不应该命中
score IS NULL    -- 应该命中
```

原因是 SQL 里的 NULL 表示 unknown，不表示一个普通值。因此 `ComparisonExpr::compare_value` 对普通比较采用“任一侧为 NULL 就返回 false”的策略，而 `IS NULL / IS NOT NULL` 才专门读取空值状态。

## 2. simple-sub-query：让 SELECT WHERE 支持简单子查询

### 2.1 功能目标

`simple-sub-query` 的目标是在 SELECT 查询中支持简单非关联子查询，包括：

- `expr IN (SELECT ...)`
- `expr NOT IN (SELECT ...)`
- `expr = (SELECT ...)`
- `expr <> / < / <= / > / >= (SELECT ...)`
- 标量子查询可以出现在比较左右两侧。
- 子查询中可以包含聚合，例如 `SELECT avg(score) FROM ...`。

官方 simple-sub-query 的主目标是简单子查询，重点覆盖非关联 `IN / NOT IN` 和标量子查询。当前代码在这个基础上还接入了相关性检测与 outer tuple 上下文，因此展示时可以说：“官方验收按简单子查询讲，当前实现主链已经预留并部分接入了相关子查询执行所需的上下文机制。”

### 2.2 为什么这样设计

miniOB 原来的 WHERE 条件主要走 `ConditionSqlNode -> FilterStmt -> ComparisonExpr` 旧链路。这条链路适合字段与常量之间的简单比较，但不适合承载子查询，因为子查询本质上不是一个普通常量，而是一段需要独立绑定、独立生成计划、独立执行的 SELECT。

因此 XC 的设计是：

- SELECT 的 WHERE 改走表达式链。
- DELETE / UPDATE 的 WHERE 继续走旧 `condition_list`，避免扩大影响面。
- JOIN ON 继续保留旧条件链，避免影响已有 join 逻辑。
- 子查询统一作为表达式节点接入，不另起第二套执行框架。

这是一种“局部升级”的做法：只把最需要支持子查询的 SELECT WHERE 切到表达式体系，其它语句先保持旧逻辑，从而降低冲突和回归风险。

这里的核心设计思路是：子查询不是“值”，而是“能产生值的表达式”。因此不能在 parser 阶段就把它简化成常量，而要保留一个表达式节点，等 binder 知道数据库、表和字段以后，再把内部 SELECT 变成完整的 `SelectStmt`。

旧链路和新链路的差别可以这样讲：

```text
旧 WHERE：
ConditionSqlNode -> FilterStmt -> ComparisonExpr
适合：字段 = 常量、字段 < 字段
不适合：右侧还要执行 SELECT

新 SELECT WHERE：
Expression -> ExpressionBinder -> PredicateLogicalOperator
适合：字段比较、IS NULL、IN 子查询、标量子查询
```

### 2.3 实现主链

`simple-sub-query` 的核心链路可以按四层解释：

- Parser / AST：新增 `sub_query` 入口，语法固定为 `(select_stmt)`；SELECT WHERE 新增表达式型 `select_where`；支持 `IN`、`NOT IN` 和标量比较子查询。
- Expression：引入或复用 `UnboundSubQueryExpr`、`SubQueryExpr`、`InSubQueryExpr`，分别表示未绑定子查询、标量子查询、集合子查询。
- Binder / Stmt：子查询绑定时递归构造内部 `SelectStmt`，要求内部 SELECT 输出列数必须恰好为 1，禁止 `select *`，并根据内部表达式是否引用外层字段设置 `correlated_` 标记。
- Plan / Execution：子查询表达式执行时复用现有 `Stmt -> LogicalPlan -> PhysicalPlan -> PhysicalOperator` 主链，把子查询结果 materialize 出来再参与外层表达式判断。
- Outer Context：当前代码中 `FieldExpr` 支持 `outer_ref_`，`SubQueryOuterContext` 使用线程局部栈保存外层 tuple；相关子查询求值时会带当前外层行重新执行。
- Cache：非关联标量子查询和非关联 `IN / NOT IN` 结果具备缓存逻辑；相关子查询会按外层 tuple 重新 materialize。

SELECT WHERE 的谓词生成也相应调整：

- `SelectStmt` 持有 `where_expression_`。
- `SelectStmt::create` 对 where expression 做 binder，并把多个条件组装成 `ConjunctionExpr(AND)`。
- `LogicalPlanGenerator` 如果发现 `where_expression()`，就直接生成 `PredicateLogicalOperator`。
- DELETE / UPDATE / JOIN ON 不走这条新链，避免互相踩线。

关键代码锚点：

- `src/observer/sql/parser/yacc_sql.y`：`select_stmt` 使用 `select_where`，而 `update_stmt` 仍使用旧 `where`。
- `src/observer/sql/parser/yacc_sql.y`：`where_predicate` 里构造 `InSubQueryExpr`，`select_subquery` 里构造 `UnboundSubQueryExpr`。
- `src/observer/sql/stmt/select_stmt.cpp`：`SelectStmt::create` 对 `select_sql.filter_exprs` 调用 `ExpressionBinder`，并生成 `where_expression_`。
- `src/observer/sql/optimizer/logical_plan_generator.cpp`：`create_plan(SelectStmt *)` 优先把 `where_expression()` 包成 `PredicateLogicalOperator`。
- `src/observer/sql/parser/expression_binder.cpp`：`bind_subquery_expression` 把 `UnboundSubQueryExpr` 转成带内部 `SelectStmt` 的 `SubQueryExpr`。
- `src/observer/sql/expr/subquery_expr.cpp`：负责子查询物理计划准备、执行、缓存和 outer tuple 上下文。

以一条 `IN` 子查询为例：

```sql
SELECT id FROM ssq_1
WHERE id IN (SELECT id FROM ssq_2);
```

流转过程可以这样讲：

1. parser 看到 `id IN (...)`，构造 `InSubQueryExpr(left=id, subquery=UnboundSubQueryExpr)`。
2. `SelectStmt::create` 绑定 WHERE 表达式；左侧 `id` 绑定成 `FieldExpr`，右侧子查询进入 `bind_subquery_expression`。
3. binder 递归调用 `SelectStmt::create` 构造内部 `SELECT id FROM ssq_2`，并检查输出列数必须是 1。
4. 逻辑计划阶段，外层 WHERE 表达式被包成 `PredicateLogicalOperator`。
5. 物理计划阶段，`prepare_subquery_expressions` 递归为内部 SELECT 生成物理执行计划。
6. 执行外层每一行时，`InSubQueryExpr::get_value` 先取左侧 id，再 materialize 子查询结果集，做成员匹配。

### 2.4 边界语义

本阶段明确收口了几个容易出错的边界：

- 子查询输出必须是单列；如果输出多列，绑定阶段报错。
- `select *` 作为子查询输出统一视为非法，包括标量子查询和 `IN / NOT IN` 子查询。
- 标量子查询 0 行的当前代码路径返回 `INVALID_ARGUMENT`，不是早期计划里的“返回 NULL”；如果官方用例要求空结果落为 NULL，需要后续调试时再调整。
- 标量子查询 1 行返回该值。
- 标量子查询多行返回错误，不能随便取第一行。
- `IN` 子查询允许多行，左值存在于右侧结果集中则为 true。
- `NOT IN` 子查询允许多行，左值不存在于右侧结果集中则为 true。
- 当前代码已经有相关性检测和 outer tuple 支持，但建议展示时仍把官方 simple-sub-query 主验收聚焦在简单子查询；复杂嵌套相关子查询不要主动扩展承诺。
- 当前代码已经有非关联缓存策略，不再是“每次求值都重复执行”的早期计划口径。

对标量子查询，可以按“单值约束”讲：

```sql
SELECT * FROM ssq_1
WHERE col1 < (SELECT avg(col2) FROM ssq_2);
```

右侧子查询必须返回一行一列。当前代码会把子查询结果收集到 `vector<Value>`：

- 如果结果数是 1，就拿这个值参与比较。
- 如果结果数大于 1，返回 `RC::INVALID_ARGUMENT`。
- 如果结果数是 0，当前 `get_value` 路径也返回 `RC::INVALID_ARGUMENT`，这个点需要后续按官方期望继续对齐。

## 3. update-select：让 UPDATE SET 右值复用查询能力

### 3.1 功能目标

`update-select` 的目标是支持：

```sql
UPDATE t SET c = (SELECT ...) WHERE ...;
```

也就是 UPDATE 的 SET 右值不再只能是简单字面量，而是可以是普通表达式或标量子查询。这样可以把查询能力和更新能力串起来，例如：

- 用另一张表的查询结果更新当前表。
- 用聚合子查询结果更新某一列。
- 按当前行逐行计算 SET 右值。

### 3.2 为什么这样设计

前面 simple-sub-query 已经形成了 `SubQueryExpr` / `InSubQueryExpr` / `UnboundSubQueryExpr` 体系。`update-select` 不需要重新实现一套子查询，而是把 UPDATE SET 右值升级为 `Expression`，然后复用已有表达式 binder 和子查询执行主链。

设计边界是：

- 扩展 `UPDATE SET` 的右值。
- 不扩展 `UPDATE WHERE` 子查询，WHERE 继续走旧 `ConditionSqlNode -> FilterStmt`。
- 标量子查询必须满足单值约束。
- 对引用当前更新行的 SET 子查询，复用 simple-sub-query 中的 `outer_ref_` 与 outer tuple 上下文。
- 更新失败时需要回滚已写入记录，避免一条 UPDATE 语句半成功。

这样能最大化复用已有 SELECT 子查询能力，同时避免把 UPDATE WHERE、DELETE WHERE、JOIN ON 全部卷入新表达式链。

这部分的核心设计可以用一句话概括：

> UPDATE 不自己理解子查询，只把 SET 右值交给表达式系统；表达式系统已经会绑定和执行子查询。

这样做的好处是复用性很高。`UPDATE t SET c = 1 + 2`、`UPDATE t SET c = (SELECT avg(x) FROM s)` 在 Stmt 和 Operator 看来都只是“求一个表达式值，然后写入字段”。

### 3.3 实现主链

`update-select` 的实现主链如下：

- Parser / AST：`update_stmt` 的 SET 右值使用 `expression`，`UpdateSqlNode` 使用 `unique_ptr<Expression> value_expr` 承载。
- Binder / Stmt：`UpdateStmt::create` 先校验目标表和目标字段，再对 SET 右值调用 `ExpressionBinder`。
- Logical Plan：`LogicalPlanGenerator` 把 `UpdateStmt::value_expr()` 移入 `UpdateLogicalOperator`。
- Physical Plan：`PhysicalPlanGenerator` 创建 `UpdatePhysicalOperator` 前，对 SET 右值里的子查询调用 `prepare_subquery_expressions`。
- Execution：`UpdatePhysicalOperator` 打开后先扫描命中行，缓存旧记录，再逐行计算 `value_expr_->get_value(row_tuple, value)` 并更新。
- Rollback：如果多行更新中途失败，按已更新记录的逆序调用回滚逻辑，尽量恢复到语句执行前状态。
- Subquery Context：当 SET 右值中的子查询引用当前更新行字段时，`FieldExpr::outer_ref_` 会从外层 `RowTuple` 取值，相关子查询逐行重新 materialize。

本轮额外收口了一个关键稳定性缺口：子查询表达式的 `copy()` 不能返回空指针。因为表达式可能在逻辑计划、物理计划、谓词重写等路径中被复制，如果遇到子查询节点直接返回 `nullptr`，后续执行会不稳定。

关键代码锚点：

- `src/observer/sql/parser/yacc_sql.y`：`update_stmt: UPDATE ID SET ID EQ expression where`，说明 SET 右值已经是通用表达式。
- `src/observer/sql/stmt/update_stmt.cpp`：`UpdateStmt::create` 通过 `ExpressionBinder` 绑定 `update_sql.value_expr`。
- `src/observer/sql/optimizer/physical_plan_generator.cpp`：创建 `UpdatePhysicalOperator` 前，对 `value_expr` 调用 `prepare_subquery_expressions`。
- `src/observer/sql/operator/update_physical_operator.cpp`：`open` 中先扫描命中记录，再逐行 `value_expr_->get_value(row_tuple, value)`。
- `src/observer/sql/operator/update_physical_operator.cpp`：`set_update_field_value` 统一处理 NULL、NOT NULL 和类型转换。
- `src/observer/sql/operator/update_physical_operator.cpp`：`rollback_updates` 在失败时逆序恢复已经写过的记录。

以一条相关 update-select 为例：

```sql
UPDATE us_t1
SET val = (SELECT score FROM us_t2 WHERE us_t2.id = us_t1.id);
```

执行过程可以这样讲：

1. parser 把 SET 右值解析成一个 `UnboundSubQueryExpr`。
2. `UpdateStmt::create` 绑定 SET 表达式，内部子查询被递归构造成 `SelectStmt`。
3. 子查询 WHERE 中的 `us_t1.id` 不在子查询本地表 `us_t2` 中，binder 会把对应 `FieldExpr` 标记为 `outer_ref_`。
4. 物理计划生成时，`prepare_subquery_expressions` 给 SET 子查询准备内部物理计划。
5. `UpdatePhysicalOperator::open` 先扫描所有符合 UPDATE WHERE 的旧记录，保存起来，避免边扫边改造成迭代混乱。
6. 对每条旧记录构造 `RowTuple`，调用 `value_expr_->get_value(row_tuple, value)`；相关子查询通过 outer tuple 读取当前 `us_t1.id`。
7. 得到新值后复制旧 record，修改目标字段，再调用 `trx_->update_record` 写入。
8. 如果中途某行失败，`rollback_updates` 按逆序把已经更新的行改回旧记录。

### 3.4 边界语义

`update-select` 的关键边界包括：

- SET 目标字段必须存在，否则保持原有非法列错误。
- SET 右值绑定结果必须恰好为一个表达式。
- 子查询输出必须是单列。
- 多行标量子查询必须报错，不能静默取第一行。
- 空标量子查询当前代码路径倾向返回错误，而不是直接赋 NULL；如果官方 update-select 明确要求空结果赋 NULL，需要后续调试确认后再调整。
- 写入前需要做类型转换。
- 写入 NULL 时必须检查目标字段是否允许 NULL。
- UPDATE WHERE 不在本题扩展子查询，仍按旧 WHERE 条件处理。
- `SubQueryExpr::copy()` 当前是安全复制体，不是完整深拷贝内部 `SelectStmt`。

为什么要“先扫描缓存旧记录，再更新”？可以这样解释：

- 如果边从 child operator 取行边更新，底层扫描器可能受更新影响，出现漏扫、重复扫或状态不一致。
- 先把命中记录缓存下来，再统一逐行更新，执行路径更可控。
- 一旦中途失败，手里还有旧记录，可以做语句级回滚。

## 4. big-query：用压力查询验证综合稳定性

### 4.1 功能目标

`big-query` 不是新增某个 SQL 语法点，而是对前面功能的综合压力验收。它的价值在于：如果点查、索引过滤、聚合、HAVING、子查询、JOIN、ORDER BY 等能力单独都能工作，那么在更大数据量下串起来也应该保持稳定。

因此本阶段目标是：

- 准备确定性的压力 SQL 生成器。
- 覆盖多个查询路径。
- 避免为了性能盲目重构执行器。
- 如果后续压力测试暴露具体问题，再做点状修复。

### 4.2 为什么这样设计

当前仓库已有 `stress-big-query` manifest 入口和 `lab/test/stress/gen_big_query_sql.py` 生成器。yys 工作区日志也记录过该题可以先通过压力资产验收，不必新增 parser 或执行器算法。

XC 的处理策略是：

- 不新增 SQL 语法。
- 不重构 join、group by、sort 等大算子。
- 只复核关键算子是否存在明显资源或状态问题。
- 只在压力脚本中补少量低风险边界查询。
- 保持最后一条 `SELECT count(*) FROM bq_main;` 作为最终验收口径。

这种策略适合 big-query 的题目定位：它更像“综合稳定性检查”，不是“新增数据库能力”。

这里的设计思路是“用稳定、确定、可复现的数据压力覆盖主链”，而不是追求随机大而全：

- 固定 seed，保证每次生成同一批 SQL，失败可复现。
- 主表 800 行、维表 20 行，数据量足以覆盖多算子组合，但不至于把展示机器拖死。
- 最后一条固定为 `SELECT count(*) FROM bq_main;`，因为测试框架会解析最后一个 `count(*)` 作为验收值。
- 不构造三表大笛卡尔积，避免把功能题变成不可解释的性能题。

### 4.3 压力测试资产

压力生成器位置：

- `lab/test/stress/gen_big_query_sql.py`

manifest 入口：

- `lab/test/manifest.json` 中的 `stress-big-query`

生成规模：

- 主表 `bq_main`：800 行。
- 维表 `bq_dim`：20 行。
- 随机种子：`SEED = 7`。
- timeout：90 秒。
- 最终期望：最后一次 `count(*)` 解析为 800。

覆盖查询类型：

- 大表主键点查：`SELECT id, v FROM bq_main WHERE id = ...`
- 索引列过滤计数：`SELECT count(*) FROM bq_main WHERE k = ...`
- 分组聚合：`SELECT k, count(*), sum(v) FROM bq_main GROUP BY k`
- HAVING：`SELECT k, avg(v) FROM bq_main GROUP BY k HAVING count(*) > 30`
- IN 子查询与排序：`SELECT id FROM bq_main WHERE k IN (...) ORDER BY id`
- 二表 join：`SELECT count(*) FROM bq_main, bq_dim WHERE bq_main.k = bq_dim.k`
- 固定 seed 的随机点查。
- 最终 `SELECT count(*) FROM bq_main;`

关键代码锚点：

- `lab/test/stress/gen_big_query_sql.py`：生成确定性 SQL，包括建表、建索引、批量插入和查询。
- `lab/test/manifest.json`：`stress-big-query` 入口，记录 generator、`expected_rows=800`、`timeout_sec=90`。
- `lab/test/run_all.py`：stress 用例会运行 generator，并解析输出里的最后一次 `count(*)`。

生成器的覆盖思路可以这样讲：

```text
建表 + 建索引
  -> 800 行主表插入
  -> 20 行维表插入
  -> 主键点查
  -> 索引过滤 count
  -> group by / having
  -> IN 子查询 + order by
  -> 二表 join count
  -> 空结果过滤与小范围排序边界
  -> 最终 count(*) = 800
```

### 4.4 本轮补充

XC 本轮在压力脚本中补了三类低风险边界：

- 空结果过滤：

```sql
SELECT count(*) FROM bq_main WHERE id=99999;
```

- join 后增加维表过滤：

```sql
SELECT count(*) FROM bq_main, bq_dim
WHERE bq_main.k = bq_dim.k AND bq_dim.label = 700;
```

- 小范围排序：

```sql
SELECT id FROM bq_main WHERE k = 3 ORDER BY id;
```

这些查询都放在最终 `SELECT count(*) FROM bq_main;` 之前，因此不会改变 `expected_rows=800` 的最终验收口径。

## 5. 四个任务之间的关系

这四个任务可以用一张逻辑链来讲：

```text
NULL 基础语义
  -> 表达式系统能处理缺失值
  -> SELECT WHERE 可以升级为表达式链
  -> 子查询可以作为表达式执行
  -> UPDATE SET 可以复用表达式和子查询
  -> big-query 用压力脚本验证组合能力
```

对应到数据库系统分层：

- `null` 更偏存储层和表达式语义基础。
- `simple-sub-query` 更偏 parser、binder、plan、execution 的查询主链。
- `update-select` 更偏 DML 与查询表达式的融合。
- `big-query` 更偏测试资产和稳定性验证。

这也能解释为什么我们负责的 1/3/5/7 组合是合理的：它不是随机选题，而是从基础语义、查询能力、更新能力到压力验收的一条连续路线。

## 6. 展示讲法建议

面向老师展示时，建议不要按“改了哪些文件”开场，而是按“数据库能力为什么需要这样补”来讲。

推荐讲述顺序：

1. 先讲 `null`：数据库不能只存普通值，还要表达缺失值，所以我们从元数据、记录布局和表达式语义补 NULL。
2. 再讲 `simple-sub-query`：有了更完整的表达式系统后，SELECT WHERE 不能再停留在简单字段比较，于是升级为表达式链并接入子查询。
3. 再讲 `update-select`：既然子查询已经是表达式，就可以复用到 UPDATE SET，让更新语句使用查询结果。
4. 最后讲 `big-query`：不是新增语法，而是用大数据量压力脚本把点查、索引、聚合、HAVING、子查询、JOIN、排序串起来验证。

如果老师追问“为什么不一次性把所有 WHERE 都改成表达式链”，可以解释：

> 为了降低回归风险，我们只把 SELECT WHERE 切到表达式链；DELETE/UPDATE WHERE 和 JOIN ON 仍保留旧条件链。这样 simple-sub-query 可以先闭环，同时不破坏已有 DML 和 JOIN 行为。

如果老师追问“big-query 为什么没有大量改执行器”，可以解释：

> big-query 的题目重点是大数据量下的稳定性和组合能力，不是要求实现新的 join 或排序算法。我们优先补压力覆盖和静态复核，只有出现明确超时、资源泄漏或结果错误时才做点状修复。

如果老师追问“当前是否全部测试通过”，建议如实回答：

> 当前文档记录的是 XC 工作区的实现主链和测试资产状态。按照团队协作约定，编译、联调和最终回归由同伴接手；因此我们不会把尚未由同伴确认的部分表述为已全部通过，只能说明代码主链、边界设计和待验证项。

如果老师追问“为什么日志和当前代码有些地方不完全一致”，建议回答：

> 开发日志记录的是阶段推进过程，中间同伴对 1/3 等任务做过修正和收口；展示文档已经回到当前代码复核，最终讲解以当前代码里的实现主链为准，日志主要作为过程留痕。
